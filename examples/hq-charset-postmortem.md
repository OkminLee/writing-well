# 예시 — 포스트모템 한 편

실제로 있었던 버그를 소재로 초고를 쓰고, 같은 재료에 `writing-well` 스킬을 걸었다. 재료는 전부 그날의 로그와 커밋에서 나왔다.

---

## 초고 (스킬 없음) — 7문단 · 751자

### HQ가 한글을 깨뜨린 이유

이번에 HQ 서버에서 마크다운 파일의 한글이 깨지는 문제를 겪었고, 그 원인과 해결 과정을 정리해봤다.

문제는 옥민이 카드로 받은 README 파일을 열었을 때 한국어가 전부 깨져 보인다고 알려주면서 드러났다. 처음에는 파일 자체의 인코딩이 잘못됐을 가능성을 의심했다. 마크다운 파일이 어딘가에서 EUC-KR로 저장됐거나, 복사 과정에서 변환이 일어났을 수 있다고 생각한 것이다.

하지만 확인 결과 파일에는 아무 문제가 없었다. 원본 README.md도, data/hq-files/에 복사된 사본도 모두 정상적인 UTF-8이었고 두 파일은 바이트 단위로 동일했다. 그렇다면 문제는 파일이 아니라 전달 과정에 있다는 뜻이었다.

서버가 내려주는 응답 헤더를 확인해보니 원인이 명확해졌다. Content-Type이 text/markdown으로만 설정되어 있고 charset 정보가 빠져 있었다. charset이 명시되지 않은 text/* 타입을 받으면 브라우저는 자체 기본값으로 해석하는데, 대부분의 브라우저는 latin-1로 폴백한다. 그래서 UTF-8로 인코딩된 한글이 깨져 보였던 것이다.

흥미로운 점은 HTML 파일은 멀쩡했다는 것이다. Bun이 HTML에는 charset=utf-8을 자동으로 붙여주기 때문이다. 이미지 파일은 애초에 텍스트가 아니므로 영향이 없었다. 결과적으로 이 버그는 마크다운, 텍스트, JSON 파일에만 나타나는 문제였다.

수정은 간단했다. /files/ 핸들러에서 charset이 없는 텍스트 계열 타입에 charset=utf-8을 붙이도록 했다. 서버를 재시작하고 확인하니 헤더가 정상적으로 나왔고, 기존에 잘 동작하던 HTML과 이미지는 영향을 받지 않았다.

결국 이번 사례에서 얻은 교훈은 증상이 나타난 지점과 원인이 있는 지점이 다를 수 있다는 것이다. 파일이 깨져 보인다고 해서 파일에 문제가 있는 것은 아니다. 계층을 하나씩 확인하는 것이 중요하다.

## REVISE 후 — 8문단 · 458자 (−39%)

### 파일은 멀쩡했다

옥민이 카드를 열고 말했다. "파일 열면 한국어가 깨져."

먼저 파일을 의심했다. EUC-KR로 저장됐거나, 복사 중에 변환됐거나. 원본 `README.md`와 `data/hq-files/`의 사본을 둘 다 찍어봤다. 둘 다 UTF-8이었고 `cmp`는 바이트 하나 차이도 못 찾았다.

파일이 멀쩡하면 배달이 깨진 것이다. 응답 헤더를 봤다.

```
content-type: text/markdown
```

charset이 없다. charset 없는 `text/*`를 받은 브라우저는 자기 기본값으로 읽고, 그 기본값은 대개 latin-1이다. UTF-8 세 바이트가 라틴 문자 세 개로 펼쳐진다. 한글만 깨지고 영문은 멀쩡했던 이유다.

HTML은 왜 멀쩡했나. Bun이 HTML에는 `charset=utf-8`을 붙여준다. 이미지는 텍스트가 아니니 무관하다. 남는 건 `.md`·`.txt`·`.json` — 아무도 헤더를 열어본 적 없는 세 확장자다.

`/files/` 핸들러에서 charset 없는 텍스트류에 `; charset=utf-8`을 붙였다. 세 줄. 재시작하고 같은 URL을 다시 찍었다.

```
Content-Type: text/markdown; charset=utf-8
```

png는 `image/png` 그대로, html도 그대로다.

깨진 화면은 파일을 가리키고 있었다. 파일은 처음부터 결백했다.

## 무엇을 왜 바꿨나

**통과 0 — 구조**

- **리드 문단을 통째로 버렸다.** "이번에 ~ 문제를 겪었고 정리해봤다"는 제목을 다시 말한 것뿐이다. 첫 문장의 유일한 일은 두 번째 문장을 읽게 하는 것이다. 실제로 나온 말 한마디로 열었다.
- **엔딩을 버렸다.** "결국 이번 사례에서 얻은 교훈은"으로 시작하는 마지막 문단은 이미 한 말의 압축이다. 독자는 이미 안다. 대신 리드에서 울린 음을 되울렸다 — 파일은 결백했다.
- **제목을 바꿨다.** 「HQ가 한글을 깨뜨린 이유」는 목차 항목이고, 「파일은 멀쩡했다」는 문장이다.

**통과 1 — 의미**

- **빠진 고리를 채웠다.** 초고는 "브라우저가 latin-1로 폴백한다 → 그래서 깨졌다"로 건너뛴다. 왜 하필 한글만 깨지는지는 필자 머릿속에만 있었다. "UTF-8 세 바이트가 라틴 문자 세 개로 펼쳐진다"를 넣으니 한 줄로 닫혔다.
- **"확인해보니 원인이 명확해졌다"를 지웠다.** 명확해진 건 필자 사정이다. 독자에게는 헤더를 보여주면 된다.

**통과 2 — 가지치기 (751자 → 458자)**

| 뺀 것 | 이유 |
|---|---|
| 흥미로운 점은 / 결과적으로 / 하지만 확인 결과 | 가치 선언어. 독자가 사실을 만나기 전에 값을 매긴다 |
| 수정은 간단했다 | 간단한지는 코드를 보고 독자가 판단한다 |
| ~할 가능성을 의심했다 → ~를 의심했다 | 부풀린 구 |
| ~하도록 했다 → ~했다 | 덧붙은 조사 |
| 마지막 문단 3문장 | 앞에서 이미 한 말 |

**통과 3 — 소리**

- **문장 길이를 흔들었다.** 초고는 전부 40~60자 한 덩어리다. "세 줄."과 "charset이 없다."를 짧게 끊어 넣었다.
- **전환 신호를 앞으로 뺐다.** "HTML은 왜 멀쩡했나"를 문단 맨 앞에 놓아 방향이 바뀌는 걸 먼저 알렸다.

## 손대지 않은 것

- **기술 용어와 경로·헤더 문자열.** 전부 원문 그대로다. 인용부호와 코드 블록 안은 한 글자도 고치지 않았다.
- **진단 순서.** 파일 → 사본 → 헤더로 좁혀간 순서가 이 글의 뼈대다. 재배열하면 글이 아니라 사건이 달라진다.
